# Диагностика неожиданного закрытия

Причину завершения устанавливают по совокупности журнала приложения, кода выхода процесса и данных Windows. Отсутствие завершающей записи само по себе не доказывает падение. Код `0` тоже не доказывает, что пользователь нажал «Выход».

## Что сохраняется

| Источник                                                  | Данные                                                                                                                      | Ограничение                                                            |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `%APPDATA%\Voxely\diagnostics\runtime-journal-*.jsonl`    | UTC, PID, идентификатор запуска, версия и сборка, запуск, готовность, причины запроса выхода, этапы обновления и завершения | 8 файлов по 256 KiB                                                    |
| `%APPDATA%\Voxely\diagnostics\process-exits\exit-*.jsonl` | Код и время выхода, раз в минуту память, CPU и число дескрипторов основного процесса                                        | 16 журналов, около 256 KiB каждый; один наблюдатель работает до 7 дней |
| `%APPDATA%\Voxely\diagnostics\dumps`                      | Минидампы Windows после аварии, если сбор явно включён                                                                      | 3 файла                                                                |

Runtime-журнал принимает только фиксированные события. В нём нет расшифровок, аудио, API-ключей, текста ошибок или содержимого panic. Для panic сохраняются имя исходного файла без пути, строка, столбец и идентификатор потока. Panic рабочего потока не обязательно завершает приложение.

Событие `previous_run_observed` со статусом `no_completion_record` означает лишь отсутствие записи о завершении. Ошибки до Tauri setup и отказ записи на диск могут остаться без runtime-журнала. Диагностика не меняет решения приложения о выходе.

## Закрытие окна и выход из процесса

`close_policy_loaded` фиксирует значение `closeToTray` при запуске, `close_policy_changed` - успешное изменение через владельца настроек в приложении, `main_window_close_decision` - значение, использованное при конкретном закрытии. Изменение файла внешней программой между запусками не имеет известного автора; новое значение будет видно при следующей загрузке.

Для главного HWND устанавливается наблюдающий subclass. `native_window_hook_installed.succeeded=true` подтверждает установку на потоке окна. Он фиксирует только `WM_SYSCOMMAND/SC_CLOSE`, `WM_CLOSE`, `WM_QUERYENDSESSION`, `WM_ENDSESSION`, `WM_DESTROY` и `WM_NCDESTROY`, передаёт каждое сообщение исходной оконной процедуре и удаляется при уничтожении окна. Нет глобальных перехватчиков ввода, текста клавиш, координат и заголовков окон. Запись из callback пропускается, если журнал уже занят.

`native_window_message.send_flags` - результат `InSendMessageEx`, а не PID отправителя. `SC_CLOSE` может прийти от крестика, системного меню или программного запроса; он не доказывает физическое действие пользователя. `WM_CLOSE` сам по себе тоже не позволяет установить отправителя. `session_ending` отражает только ненулевой `wParam` у `WM_ENDSESSION`.

`main_window_hidden` означает намерение скрыть окно. Результаты операций фиксируются отдельно в `main_window_hide_result`; `main_window_shown` отражает результат повторного показа. При `closeToTray=true` крестик должен скрывать окно, оставляя процесс работающим. При `false` существующая настройка требует выхода. Причины выхода через трей, обновление и локальную пересборку имеют отдельные `exit_intent.reason`.

## Локальный запуск и наблюдатель

Канонический запуск: `pwsh -NoProfile -File scripts/start-local-app.ps1`. Пересборка `bun run rebuild:local-app` вызывает его автоматически. Скрипт проверяет точный release exe, видимое окно и запуск вне Windows Job командного окружения, затем подключает отдельный скрытый наблюдатель.

Для уже запущенной локальной сборки: `pwsh -NoProfile -File scripts/rebuild-local-app.ps1 -StopRunning`. Отдельный `scripts/stop-local-app.ps1` выбирает только точный release exe и передаёт `--quit-for-local-rebuild=<PID>` через существующий single-instance канал. Приложение принимает запрос только в локальной сборке, для собственного PID и при отсутствии активной диктовки, обработки, вставки, сравнения или установки обновления. Проверка занятости и запрет новых операций выполняются под существующими блокировками сессии и admission. Скрипт ждёт конкретный процесс максимум 40 секунд, не завершает его принудительно и не меняет настройки. В старых сборках используйте «Выход» в трее; закрытие крестиком может лишь скрыть окно. Если адресат уже исчез, контрольный запуск не открывает новую Voxely и завершается с кодом 2.

Контрольный callback не ждёт завершения сессии на потоке интерфейса: работа передаётся отдельному worker. Если lifecycle или admission уже заняты, `try_lock` немедленно отклоняет запрос как `busy`. После отказа повторять запрос следует только после завершения работы.

Обычный выход из трея, закрытие при `closeToTray=false` и запрос выхода Tauri обслуживает единый worker. Первый принятый запрос задаёт действие `Exit(code)` или `Restart`; повторные запросы не создают второй cleanup. Блокировки сессии освобождаются до оконных API. Callback завершения захвата не ждёт lifecycle для финального exit; при конкуренции владелец повторяет проверку до прежнего лимита 30 секунд, затем сохраняется прежний путь ограниченного принудительного завершения. Сбой создания worker фиксируется как `shutdown_worker_unavailable` и освобождает ownership для повтора.

Tauri 2.12.1 не позволяет отклонить `RESTART_EXIT_CODE` через `prevent_exit`. Поэтому собственные updater callers запрашивают typed Restart до входа в Tauri, а `request_restart()` вызывается после cleanup. Неиспользуемое разрешение прямого frontend restart удалено. Неожиданный обход владельца будет отмечен `uncoordinated_restart`; такое событие не доказывает успешную очистку. Windows updater отдельно завершает процесс внутри плагина после запуска установщика: его `update_installer` остаётся намерением, а не подтверждением завершения.

Наблюдатель держит дескриптор конкретного процесса с проверкой PID и времени запуска. Он не перезапускает и не завершает Voxely. Повторное подключение переиспользует живого наблюдателя. Его отдельный PowerShell-процесс расходует дополнительную память; это временная диагностика. Метрики относятся только к основному процессу Voxely, без дерева WebView2.

После истечения 7 дней наблюдатель завершится с записью `observer-expired`. Подключить его заново: `pwsh -NoProfile -File scripts/start-exit-monitor.ps1 -TargetProcessId <PID>`. При обычном следующем локальном запуске новый наблюдатель подключается автоматически.

## Минидампы Windows

Сбор включается отдельно и требует повышения прав. Запуск приложения настройки WER не меняет. Скрипт `configure-crash-dumps.ps1` использует только per-app ключ `LocalDumps\voxely.exe`: `DumpType=1`, `DumpCount=3`. Он не меняет глобальные настройки и отказывается заменять чужую конфигурацию.

Проверка: `pwsh -NoProfile -File scripts/configure-crash-dumps.ps1 -Mode Status`.

Включение из повышенного PowerShell: `pwsh -NoProfile -File scripts/configure-crash-dumps.ps1 -Mode Enable`.

После расследования отключить из повышенного PowerShell: `pwsh -NoProfile -File scripts/configure-crash-dumps.ps1 -Mode Disable`. Отключение проверяет запись владения и текущие значения; собранные дампы остаются. Автоматического отключения по времени нет.

Ключ применяется к процессам с именем `voxely.exe`. Минидамп может содержать приватные фрагменты памяти. Файлы остаются локально. Принудительное завершение процесса или отключение питания может не создать дамп. Подробнее: [Microsoft WER LocalDumps](https://learn.microsoft.com/en-us/windows/win32/wer/collecting-user-mode-dumps).

## Собрать архив

Команда из корня репозитория: `pwsh -NoProfile -File scripts/collect-crash-diagnostics.ps1`.

Архив сохраняется в `.local\diagnostics`. Он содержит метаданные процесса и бинарника, хвосты двух обычных журналов, до восьми runtime-журналов и шестнадцати журналов наблюдателя, статус WER и события Application за последние 24 часа. Чтение каждого текстового файла ограничено 128 KiB и 300/400 строками. Запрос Windows events ограничен 20 секундами, 80 просмотренными и 30 включёнными событиями. Насыщенный журнал Windows может вытеснить более ранние события из этого окна.

Чтобы явно включить дампы: `pwsh -NoProfile -File scripts/collect-crash-diagnostics.ps1 -IncludeDumps`. Копируется максимум три завершённых файла, каждый до 32 MiB. Занятые и слишком большие дампы пропускаются со статусом в `collection.json`; исходные файлы остаются на месте.

Файлы истории, настроек и аудио напрямую не читаются. Обычные логи и дампы могут содержать приватные данные: перед передачей архива проверьте его содержимое. Ничего автоматически не отправляется. ZIP пишется напрямую, без временной распакованной папки.

## Проверки самих скриптов

Общий запуск: `pwsh -NoProfile -File scripts/check-diagnostics.ps1`. Он включён в `bun run verify` и Windows CI. Проверки не требуют прав администратора.

- `pwsh -NoProfile -File scripts/watch-local-app.ps1 -TargetProcessId 0 -ExpectedStartTicks 0 -SelfTest` проверяет получение кода `7` от отдельного тестового процесса.
- `pwsh -NoProfile -File scripts/start-exit-monitor.ps1 -TargetProcessId 0 -SelfTest` проверяет поиск исходного подключения после 40 samples и частичной записи.
- `pwsh -NoProfile -File scripts/collect-crash-diagnostics.ps1 -SelfTest` проверяет ограничение копируемых байтов, EOF и длинную строку.

Эти проверки не вызывают падение пользовательской Voxely и не доказывают создание WER-дампа при реальной аварии.
